# الأمان (Security)

مبدأ عام: **Defense in depth** — لا نعتمد على طبقة واحدة. كل قاعدة مهمة تُفرض في ثلاثة أماكن عند الإمكان: الـ API (صلاحيات)، الـ service (منطق)، وقاعدة البيانات (constraints).

## 1. المصادقة (Authentication)
| البند | القرار |
|---|---|
| تسجيل الدخول | **واتساب OTP فقط** لكل الأنواع؛ لا بريد ولا كلمات مرور (لا شيء يُنسى أو يُسرَّب أو يُخمَّن) |
| الرمز | 6 أرقام عشوائية (`secrets`)، 5 دقائق، استخدام واحد، يُخزَّن HMAC فقط، 5 محاولات ثم يُحرق |
| JWT | access token **10–15 دقيقة**، refresh **7 أيام** مع Rotation + Blacklist بعد الاستخدام |
| تسجيل الخروج | إبطال refresh token (blacklist) |
| 2FA | الرمز نفسه عامل التحقق الوحيد. **تخفيف المخاطر للإدارة:** Step-up OTP (رمز جديد) قبل العمليات الحساسة، وتنبيه واتساب عند كل دخول لأدمن (مرحلة لاحقة) |
| قفل الحساب | بعد 5 محاولات فاشلة: تأخير تصاعدي/قفل 15 دقيقة + تنبيه |
| فقدان الرقم | يتم عبر الأدمن (تغيير رقم الموظف) بعد التحقق خارج النظام؛ لا مسار استرداد ذاتي |
| الجلسات | إبطال كل التوكنات عند تعطيل الحساب؛ Logout يُبطل الـ refresh |
| API للأنظمة | مفاتيح API مجزّأة (hash) بنطاق صلاحيات محدود، قابلة للإبطال |

### الدخول/التسجيل عبر واتساب (OTP)
- الرمز 6 أرقام عشوائية (`secrets`)، صلاحية 5 دقائق، **يُخزَّن HMAC فقط**، ويُبطل الرمز السابق عند إصدار جديد، ولا يُستخدم إلا مرة واحدة.
- حد 5 محاولات خاطئة للرمز ثم يُحرق؛ مهلة 60 ثانية بين الإرسالات، و5 رموز/ساعة لكل رقم، وThrottling لكل IP.
- رد الإرسال متطابق سواء وُجد حساب أم لا (منع تعداد الأرقام).
- فشل الإرسال يُلغي الرمز ولا يفرض مهلة على المستخدم.
- **الموظف والأدمن يدخلون بواتساب أيضاً** (قرار منتج). **المخاطرة:** من يسيطر على رقم موظف/أدمن (SIM swap، واتساب ويب مفتوح) يصبح بصلاحياته. التخفيف: Step-up OTP للعمليات الحساسة، تنبيه دخول، حد 15 دقيقة لـ access، تعطيل فوري من الأدمن الآخر، وحماية آخر أدمن من التعطيل. يُنصح بتفعيل التحقق بخطوتين داخل واتساب نفسه لأرقام الإدارة.
- مفتاح API الخاص بواتساب في متغير بيئة `WHATSAPP_API_KEY` فقط، لا في الكود ولا السجلات ولا الوثائق. الرمز لا يُكتب في AuditLog.
- المخاطرة المقبولة: سرقة الرقم (SIM swap) تعني الوصول لحساب زبون؛ لا يمس صلاحيات إدارية.

## 2. التفويض (Authorization)
- **RBAC ديناميكي يديره الأدمن:** `user_type` (customer/staff) + أدوار + صلاحيات مباشرة (allow/deny) + نطاقات (مخزن، حد مبلغ/خصم) + صلاحيات مؤقتة بتاريخ انتهاء. التفاصيل في `02-database-design.md`.
- **قواعد الحماية:**
  - الرفض افتراضي: موظف بلا دور = بلا وصول.
  - كل endpoint يعلن صلاحيته (`required_permission`)؛ endpoint بدون إعلان يفشل في اختبار CI.
  - لا يمنح أحد صلاحية لا يملكها (منع تصعيد الصلاحيات)؛ منح `users.*` للأدمن فقط.
  - حماية آخر أدمن من الحذف/التعطيل/سحب الصلاحية.
  - تغيير الصلاحيات يُبطل الكاش وتوكنات المستخدم فوراً، ويُسجَّل في AuditLog.
  - الزبون (`customer`) لا يستطيع نيل صلاحيات إدارية مهما حصل (قيد على مستوى DB + الخدمة).
  - الأمر الواجب فحصه في الخادم وليس الواجهة؛ الواجهة تخفي العناصر فقط.
- **Object-level:** الزبون يصل لطلباته/عناوينه/سلته فقط؛ كل queryset في الـ Storefront يُفلتر بالمستخدم افتراضياً (`get_queryset` الأساسي) — لا يُعتمد على الـ view لتذكّر الفلترة.
- **فصل الواجبات (Maker–Checker):**
  - من أنشأ قيداً يدوياً لا يرحّله.
  - تعديل مخزون يتجاوز حداً قابلاً للضبط يحتاج موافقة ثانية.
  - إلغاء/استرداد طلبية مدفوعة يحتاج صلاحية أعلى.
  - تغيير الأسعار الجماعي وإغلاق الفترة: Admin/Accountant فقط.
- **منع IDOR:** معرّفات عامة UUID، مع التحقق من الملكية رغم ذلك.
- **Mass assignment:** serializers بحقول صريحة (`fields = [...]`)؛ الحقول الحساسة (`status`, `total`, `amount_paid`, `unit_cost`, `role`) للقراءة فقط وتتغير عبر services.
- **صلاحيات افتراضية = رفض:** `DEFAULT_PERMISSION_CLASSES = [IsAuthenticated]`، وأي endpoint عام يُصرَّح عنه صراحة.

## 3. حماية البيانات
- **النقل:** HTTPS فقط، HSTS، `SECURE_SSL_REDIRECT`، كوكيز `Secure/HttpOnly/SameSite`.
- **السكون:** تشفير قرص قاعدة البيانات والنسخ الاحتياطية؛ تشفير على مستوى الحقول لأي بيانات شديدة الحساسية (إن وُجدت).
- **الأسرار:** في متغيرات البيئة/مدير أسرار، لا في الكود ولا Git؛ `.env` في `.gitignore`؛ تدوير المفاتيح.
- **بيانات الدفع:** **لا تُخزَّن بيانات البطاقات إطلاقاً**؛ نخزّن مرجع/توكن البوابة فقط (PCI SAQ-A).
- **تقليل البيانات:** لا نرجع حقولاً غير لازمة؛ إخفاء بيانات شخصية في السجلات (logs).
- **الخصوصية:** تصدير/حذف بيانات الزبون عند الطلب (إخفاء الهوية Anonymize بدل الحذف للسجلات المالية).

## 4. سلامة البيانات المالية
- القيود المرحّلة وحركات المخزون **append-only**: صلاحيات قاعدة البيانات لا تمنح `UPDATE/DELETE` عليها لحساب التطبيق، أو trigger يمنعهما.
- **Constraint trigger** يفرض توازن القيد على مستوى PostgreSQL.
- التسعير من الخادم دائماً؛ يتجاهل الـ checkout أي سعر/خصم/إجمالي يرسله العميل.
- **Audit Log غير قابل للتعديل:** append-only، يسجّل: الدخول/الفشل، تغيير الأدوار، تعديل الأسعار، حركات المخزون اليدوية، الترحيل/العكس، إغلاق الفترات، الإلغاءات، التصدير. حقول: actor, ip, user_agent, action, object, before/after, at. (اختياري لاحقاً: سلسلة hash لكشف العبث.)
- حسابا قاعدة بيانات: `app_user` (بصلاحيات محدودة) و`migrator` (للـ migrations فقط).

## 5. أمان الـ API
- **Rate limiting (DRF Throttling + cache):** send-code 10/ساعة/IP و5/ساعة/رقم، verify 30/ساعة/IP، checkout بحدود صارمة، الـ Storefront للمجهول حد عام.
- **CORS:** قائمة أصول مسموحة صريحة لكل واجهة (إدارة / متجر)، لا `*`.
- **CSRF:** لا ينطبق على JWT في الـ header؛ إن خُزّن refresh في كوكي → `SameSite=Strict` + CSRF.
- **التحقق من المدخلات:** كل المدخلات عبر serializers؛ حدود على الأطوال والأحجام وعمق JSON وعدد عناصر الـ bulk.
- **SQL Injection:** ORM فقط؛ ممنوع تجميع SQL نصياً (أي استثناء يُراجع).
- **XSS:** الـ API يرجع JSON؛ تنقية HTML في أوصاف المنتجات (allowlist مثل `nh3`) و`Content-Security-Policy` في الواجهات.
- **رفع الملفات:** التحقق من النوع الفعلي (magic bytes) والحجم، إعادة تسمية، تخزين خارج الجذر العام/على storage مع روابط موقّعة، فحص الصور (Pillow reopen)، منع SVG النشط.
- **Pagination إلزامية** وحد أقصى لـ `page_size` لمنع استنزاف الموارد.
- **رؤوس الأمان:** `X-Content-Type-Options`, `X-Frame-Options/frame-ancestors`, `Referrer-Policy`.
- **رسائل الأخطاء:** لا تسريب stack traces؛ `DEBUG=False` في الإنتاج؛ `ALLOWED_HOSTS` صارم.
- **فصل الواجهتين:** `admin.` و`api.`/المتجر على نطاقات/إعدادات منفصلة؛ لوحة Django admin معطّلة أو مقيّدة بشبكة/VPN و2FA.

## 6. أمان المتجر العام (Storefront)
- حماية من الـ bots في التسجيل/الـ checkout/كلمة المرور (CAPTCHA أو Turnstile).
- منع enumeration: ردود موحّدة لتسجيل الدخول والاسترداد.
- منع التلاعب: التحقق من توفر المخزون والسعر والعملة والكوبون على الخادم لحظة الـ checkout.
- **Webhooks بوابة الدفع:** التحقق من التوقيع، idempotent، قائمة IP مسموحة إن أمكن، وإعادة التحقق من حالة الدفع من البوابة مباشرة.
- حماية من حجز المخزون الخبيث (استنزاف المخزون بسلال/طلبات وهمية): حدود لعدد الطلبيات المعلّقة وانتهاء صلاحية الحجز.
- منع الدفع الجزئي/المكرر: `Idempotency-Key` + فرادة مرجع الدفعة.

## 7. البنية التحتية
- حاويات بمستخدم غير root، صور ثابتة الإصدار، فحص ثغرات الصور (Trivy).
- قاعدة البيانات غير مكشوفة للإنترنت (شبكة خاصة).
- **نسخ احتياطي:** يومي + WAL/PITR، تشفير، نسخة خارج الموقع، **اختبار استعادة دوري** (فصلي)، أهداف: RPO ≤ 15 دقيقة، RTO ≤ 4 ساعات (قابلة للتعديل).
- مراقبة وتنبيه: Sentry للأخطاء، تنبيهات على: فشل دخول متكرر، قيود غير متوازنة، رصيد مخزون سالب (يجب ألا يحدث)، خطأ 5xx.
- سجلات مركزية بتدوير زمني؛ لا بيانات حساسة فيها.

## 8. سلسلة التوريد وعملية التطوير
- تثبيت الإصدارات (`requirements.lock`)، فحص دوري بـ `pip-audit` و`dependabot/renovate`.
- `bandit` + `ruff` في CI، `detect-secrets` في pre-commit.
- مراجعة كود إلزامية للتغييرات المالية/الصلاحيات، وفرع main محمي.
- مراجعة أمنية قبل كل إصدار (OWASP ASVS L2 كمرجع، وOWASP API Top 10).

## 9. الاختبارات الأمنية (إلزامية لكل مرحلة)
1. **صلاحيات:** مصفوفة اختبارات (دور × endpoint) تتأكد من 401/403 الصحيحة.
2. **IDOR:** زبون A لا يقرأ/يعدّل بيانات زبون B (طلبات، عناوين، سلة، دفعات).
3. **Mass assignment:** إرسال `total`/`status`/`role` في الطلب يُتجاهل.
4. **التزامن:** طلبان على آخر وحدة؛ دفعتان متزامنتان؛ ترقيم مستندات بدون تكرار.
5. **المالية:** قيد غير متوازن يُرفض؛ ترحيل في فترة مغلقة يُرفض؛ تعديل قيد مرحّل يُرفض (حتى مباشرة على قاعدة البيانات).
6. **Idempotency:** تكرار checkout بنفس المفتاح يعيد نفس الطلبية.
7. **Throttling:** تجاوز الحد يرجع 429.
8. **رفع الملفات:** ملف مزيّف الامتداد يُرفض.

## 10. الاستجابة للحوادث
- دليل مختصر: كشف ← احتواء (إبطال توكنات/مفاتيح، تعطيل حساب) ← استرجاع ← مراجعة.
- القدرة على **إبطال كل الجلسات** وتدوير `SECRET_KEY` عند الحاجة.
- الاحتفاظ بسجل التدقيق مدة لا تقل عن 12 شهراً.
